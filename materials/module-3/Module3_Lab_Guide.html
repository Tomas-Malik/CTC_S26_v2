Data On Demand: Build It, Break It, Fix It

Your step-by-step guide for both beats. Work at your own laptop, alongside your AI assistant — this page tells you what to do, not what to type.

Level 2 Prerequisite: Module 2 Bring a laptop + AI assistant

“A living tool doesn’t remove the work — it converts it from ‘redo the report’ into ‘notice when it breaks.’ That job doesn’t go away just because the report updates itself.”

Quick recap of where we are: Module 2 left you with a report on Pinnacle Peak Home Services that took real work to get right. The Director loved it — so much that she doesn’t want a deck anymore. She wants to check the numbers herself, whenever she wants. Today you build that: an actual webpage, running on your own machine, that reads a data folder and stays current. Then you find out what “stays current” really costs.

Beat One — Build the living report

Goal: leave this beat with a real, running webpage on your machine — not a description of one.

  1. Get the starting materials
    Download Module3_LivingReport_Starter.zip from the module page and unzip it. Inside: a data/ folder with four years of Pinnacle Peak revenue spreadsheets, and nothing else built yet.
  2. Hand it to your AI assistant
    Tell it what you want in plain language: a webpage, built from the files in data/, that runs locally and stays useful as the data changes — not a one-time export. Let it ask you questions or make its own calls on how to build it.
  3. Get it actually running — served, not just opened
    A file you double-click isn’t “served.” If your assistant hands you an HTML file and nothing else, ask it specifically to run it as a local webpage (most AI assistants can start a local server for you and give you a localhost address to open). This is what “on their PC” means for today.
  4. Push past a static image
    Check your build against the MVP checklist below. If all you have is a picture of a chart, tell your assistant what’s missing and ask for another pass — this is exactly the kind of back-and-forth the module’s first big idea is about.

MVP checklist — what “done” means for Beat One

  • It opens from a localhost address in a browser, not a double-clicked file.
  • It shows the Pinnacle Peak revenue data as more than a static picture — a real chart, not a screenshot of one.
  • At least one filter (e.g. show/hide a service line or a date range).
  • At least one sort (e.g. a table you can re-order by column).
  • At least one toggle (e.g. switch between two views of the same data).
  • You can point to where it reads its data from, and explain that in one sentence.

Stretch — if you have time

Sketch what handing this to IT for real would take. You don’t have to actually do it — just answer, in a few bullet points, with your AI assistant’s help:

  • Where would this actually live so anyone at Pinnacle Peak can reach it — not just your laptop?
  • Who’s allowed to put new files in the data folder, and how do they get them there safely?
  • What happens if the site goes down at 2am — whose problem is that?
  • What would you literally put in the email to IT asking for this?

Beat Two — New numbers, hit rebuild

Goal: put new data in the folder, rebuild, and handle whatever happens next.

  1. Get the new numbers
    Download Pinnacle_Peak_Revenue_2026_H2.xlsx from the module page. Second half of the year, same company, same shape of file as the ones you already have.
  2. Drop it in the folder
    Put it alongside the other files in data/ — don’t rename it, don’t open and re-save it, don’t edit it. Just add it, the way new data actually shows up.
  3. Hit rebuild
    Re-run whatever your assistant set up to regenerate the report (the “build” or “rebuild” step from Beat One), then refresh the page in your browser.
  4. Look before you assume it worked
    “It didn’t crash” is not the same as “it worked.” Check the report against what you’d expect now that six more months of data exist. Use whatever the report shows you — totals, date ranges, a log, anything — before deciding it’s fine.

If something looks off

Don’t hand-edit the report, the generated data file, or anything under report/ to make it look right — that fixes the symptom for exactly one rebuild and hides the real problem from the next person. Go back to your AI assistant, describe what looks wrong, and work through it together: where does this report’s data actually come from, and what changed between the file that worked and the one that didn’t? Your assistant can inspect both files directly — use that.

The two moves this beat is actually testing

Notice: catching that a successful-looking rebuild isn’t actually right. Fix: finding the real cause in the pipeline and correcting it there — not patching the output. Both are skills you’ll use on every “living” thing you ever build, not just this one.

Two things to leave with

  • 1

    AI supplements your technical skills

    You just built and ran an actual local webserver and an interactive webpage — probably without writing most of the code yourself. That’s not a toy exercise; it’s a real capability now sitting a lot closer to hand than it used to.

  • 2

    It's not magic — maintenance is real

    Beat Two happened because that’s what living tools actually do: they keep needing attention. Hosting, upkeep, and breakage don’t go away because AI helped you build the thing — a living tool trades one-time report-writing for ongoing tech debt. Worth knowing which one you’re signing up for.

Keep both beats’ output around if you can — your facilitator may ask what you built and what broke, not just whether you finished.
