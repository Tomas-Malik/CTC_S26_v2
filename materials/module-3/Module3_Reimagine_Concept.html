Data On Demand: From Static Report to Living Webpage

Grounding notes for a reimagined Module 3. Captured so the next pass has the new shape in hand, not the old one.

Status: reimagine, not built Level 2 Prerequisite: Module 2

Where this stands

This supersedes the existing Level 1 Module 3 build (the chart-picking / dashboard deck already in the folder). The reimagine keeps the Pinnacle Peak scenario and the assistant-vs-analyst backbone, but replaces both beats with a hands-on build-and-break exercise. Nothing below has been built or tested with learners.

Structural change: Level 2

Module 3 moves from Level 1 to Level 2, with Module 2 as an explicit prerequisite — the only leveled-up module in the curriculum; Modules 1, 2, and 4 stay Level 1. The reimagined build asks learners to produce and maintain a working artifact (a live webpage), not just a document, which is a real jump in what's assumed walking in.

Proposed throughline

“A living tool doesn’t remove the work — it converts it from 'redo the report' into 'notice when it breaks.' That job doesn’t go away just because the report updates itself.”

The two reimagined beats

Same Pinnacle Peak folder as the current build. Both beats are rewritten.

  • 1

    Beat 1 — build the living report

    Not a static file this time: learners have AI build an actual webpage, served locally on their own machine, that reads the data folder and renders the report — with a minimum viable set of interactive features (filter, sort, a toggle, something beyond a static image). The stretch goal: sketch what handing this off to IT for real hosting would take, even if that step isn't executed in the room.

  • 2

    Beat 2 — new numbers, hit rebuild, make it break

    Drop new data into the folder and rebuild — but this time the new data is designed to break something (a format change, a bad row, a missing column, whatever's easiest to engineer reliably). The exercise is entirely about the two moves that follow: noticing the rebuild produced something wrong, and fixing it. This is the diagnostic beat, rebuilt around a technical failure instead of a content-judgment one.

Big ideas

  • 1

    AI supplements your technical skills

    Open the learner's imagination to what's now reachable without being an engineer — a working, interactive webpage built and maintained with AI as the technical partner, not just a writing or analysis one.

  • 2

    It's not magic — maintenance is real

    Ground the excitement from Beat 1 in the reality Beat 2 delivers: hosting, upkeep, and breakage are real, ongoing costs. A living tool trades one-time report-writing for ongoing tech debt — a fair trade, but not a free one, and learners should leave knowing which they signed up for.

Open questions before this can be built

  1. Local serving mechanics: what "served on their PC" actually means in a workshop setting — a simple local server AI sets up for them, or something more manual, and what's assumed about their machine.
  2. The IT hand-off: how far Beat 1's "hand-off to IT" goes — a real conversation about hosting requirements, or just a prompt that gets learners naming what they'd need to ask for.
  3. The planted break: what specific failure Beat 2 engineers into the new data — needs to be reliable to reproduce and diagnosable without being a lucky guess.
  4. Diagnostic guide: the checklist equivalent to Modules 1 and 3's existing diagnostics, but for "did they notice, and did they actually fix it" on a technical break.
  5. Prerequisite enforcement: whether Level 2 / "Module 2 required" is just a note on the page, or something the delivery format actually gates.

Prepared as a starting point for whoever picks this reimagine up — not a commitment to the exact mechanics above.
